# Review Protocol

レビューと監査に共通する手順と出力の型を定める。何を見るか（観点）と、その分野固有の質問は各レビュー Skill が持つ。この Skill はそれを含まない。

## 手順

1. 基準を確定する。
2. 足りない入力を洗い出し、ヒアリングするかを決める。
3. 各レビュー Skill の観点でレビューする。
4. 出力の型で返す。

## 1. 基準の確定

- 対象に関係する仕様（要求、ADR、規約、品質の水準）を探して読む。プロダクトREADMEがあれば、そこから辿る。
- 観点を、要求に照らすものと、一般的な基準（公式ドキュメント、標準、各 Skill が根拠に挙げる資料）に照らすものに分ける。
- 仕様がある場合: 一般的な観点でレビューしたうえで、特に仕様を満たしているかを精査する。要求ごとに、満たしているか・満たしていないか・判断できないかを示す。
- 仕様がない場合: 一般的な観点でレビューする。出力の「基準」に、一般的な観点だけでのレビューであり、目的に合っているかは確かめていないことを明記する。
- 仕様の一部だけがある場合は、仕様がある部分とない部分を分けて扱う。

## 2. 事前ヒアリング

- 先に文書を読む。文書で分からず、結果を左右する情報だけを、足りない入力として挙げる。
- 足りない入力がある場合は、ヒアリングするか、前提を置いて進めるかをユーザーに選んでもらう。前提を置いて進める場合は、置いた前提を出力の「前提と範囲」に書く。
- 足りない入力がなければ、聞かずに始める。
- 問いは、聞くこと・答えがないときに置く前提・なぜ聞くか（答えで何が変わるか）の組で示す。

どのレビューにも共通して、次を確かめる。文書で分かる項目は聞かない。

| 項目 | 聞くこと | 精度が上がる理由 |
| --- | --- | --- |
| 目的 | このレビューで何を決めたいか（採用、公開の可否、改善点の洗い出しなど） | 判定の基準と、結論の書き方が変わる |
| 範囲 | どこまで見るか。見なくてよいもの | 見なかった所を問題なしと誤解させない |
| 基準 | 守る要求・規約・品質の水準 | 指摘が要求に結び付き、好みの指摘が減る |
| 前提・制約 | 規模、期限、意図した妥協 | 意図した妥協を問題として指摘しない |
| 厳しさ | 必須だけか、推奨までか、検討まで出すか | 出力の量を目的に合わせられる |
| 気になっている点 | 特に見てほしい所 | 見る順番と深さを決められる |

分野固有の質問は、各レビュー Skill の定めに従う。

## 3. 出力の型

結論から書き、次の順で返す。該当がない節は「なし」と書き、節を消さない。

```md
## 結論
総合判定と、その理由を1〜3行。

## 基準
何に照らしたか（仕様の ID、ヒアリングで得た基準、外部の資料）。仕様がない場合は、一般的な観点だけのレビューであることをここに書く。

## 前提と範囲
- 置いた前提
- 見た範囲・見なかった範囲（各 Skill の観点のうち、通したもの・通さなかったもの）

## 評価の要約
| 観点 | 評価（良い／要改善／問題） | 重さ | なぜ | 根拠 |

## 良い点
- 残すべき点と、その理由

## 指摘の詳細
### R-01 要旨
- 重さ:
- 場所:
- 事実: 何がどうなっているか
- 影響: なぜ問題か、放置すると何が起きるか
- 根拠: 「基準」のどれに照らしたか
- 確かさ: 確認済み／推測
- 提案:

## 判断できなかったこと
入力や仕様が足りずに判定を保留したもの。

## 次にやること
```

- 重さは、各 Skill に定めがあればそれに従う。定めがなければ、次の3段階とする。
  - 必須: 要求に反する、データが壊れる・失われる、セキュリティ上の危険がある。直すまで受け入れない。
  - 推奨: 受け入れは止めないが、直すべきもの。
  - 検討: 任意の改善。
- どの段階が受け入れを止めるかを、結論と要約で分かるようにする。
- 根拠は「基準」のどれかを指す。基準に結び付かない指摘は、問題として出さず、確認したいこととして出す。
- 事実と判断を分ける。推測は、推測であることを「確かさ」に書く。
- 各 Skill が追加の節を定める場合は、「次にやること」の前に置く。
