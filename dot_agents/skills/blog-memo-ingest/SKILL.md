# Blog Memo Ingest

ユーザーから渡されたメモを、Astro Markdown Blog の記事メモ欄へ転記するための workflow。転記の仕方（原文＋軽い整理／原文のまま／体裁を整える／加筆・修正を含める）はユーザーに選ばせる。

対象リポジトリは `astro-markdown-blog` を想定する。別リポジトリで使う場合は、同等の Markdown 記事構成、frontmatter、メモ欄見出しがあるか確認してから使う。

## Hard Rules

- このスキルは `## メモ` 欄への転記だけを行う。本文（`## メモ` より上の部分）は空にし、要約・観点を含む依頼された内容はすべて `## メモ` の中に置く。
- `## メモ` 欄への転記方法は、ユーザーに次の4モードから選ばせる。
  - `原文＋軽い整理`: 原文を `### 原文` に残し、`### 要約` に内容を増やしすぎない短い要約を、`### 観点` に記事化に役立つアシスタントの観点を追記する。原文・要約・観点を混在させない。
  - `原文のまま`: 文字は一語一句変えない。要約、校正、表記ゆれ修正、語句の追加・削除・並べ替えを行わない。ただし原文の構造が崩れて渡された場合は、構造だけを Markdown の記法へ写し直す（「構造の復元と記法」に従う）。
  - `体裁を整える`: 内容・意味・情報量を変えずに、見出し、箇条書き、改行などの体裁だけ整える。文意の追加・削除はしない。`原文のまま` との違いは、原文に痕跡がない見出しの追加や、箇条書きへの組み替え、改行位置の変更まで行ってよい点にある。
  - `加筆・修正を含める`: 内容の加筆・修正・言い回しの変更を伴う編集を許可する。この場合、元のメモ原文を併記して残すかどうかを都度ユーザーに確認する。
- モードが未指定・未回答の場合は `原文＋軽い整理` をデフォルトとする。
- このモード選択は `## メモ` 欄への転記にのみ適用する。記事本文をどう書くかの方針とは独立に扱う（本文の執筆方針は別途「編集方針」の確認で決める）。
- 1つのメモから複数記事を作る場合は、各記事に関係する原文だけを分割して載せる。共通の原文を全記事へ複製しない。分割先が曖昧な原文は、勝手に配分せずユーザーへ確認する。
- 対象記事が未確定の場合は、候補を出してユーザーに確認する。
- 既存記事への追記、新規記事作成、frontmatter 提案、`## メモ` 転記モードの選択のいずれも、編集前にユーザーの明示的な OK を得る。
- 新規記事を作る場合は、タイトル、slug、カテゴリ、frontmatter を提案し、承認後に作成する。
- `## メモ` の固定見出しを使う。
- メモ欄は1記事につき1つだけにする。
- Git 操作、Notion 更新、既存記事本文のリライトは、明示指示がない限り行わない。
- 原文に痕跡がない構造（テーブル、トグル、チェックリスト、コールアウトなど）を勝手に足さない。痕跡がある構造は、転記モードに関わらず復元してよい。判断は「構造の復元と記法」に従う。

## 前提運用

記事は `src/content/posts/blog/*.md` に置く。

公開状態は frontmatter の `status` で管理する。

- `private`: 非公開。書いたが公開をやめたい記事、公開対象にしない記事
- `draft`: 執筆中で、公開する意思がある記事
- `published`: 公開記事

執筆状態は `writingStatus` で管理する。

- `writing`: 進行中
- `planned`: 進行予定
- `todo`: 未着手
- `on_hold`: 保留
- `done`: 執筆完了

優先度は `priority` で管理する（必須）。

- `high` / `medium` / `low`: 優先度
- `none`: 未設定

メモ欄は次の形式にする。

```md
## メモ

ここにメモを書く
```

## Workflow

1. ユーザーが追加したいメモ本文を確定する。
2. 確定したメモ本文をそのままユーザーに提示し、内容に過不足がないか確認する。
3. `## メモ` 欄への転記モードをユーザーに選ばせる（原文＋軽い整理／原文のまま／体裁を整える／加筆・修正を含める）。
   - 「加筆・修正を含める」を選んだ場合は、元のメモ原文を併記して残すかどうかも確認する。
4. `src/content/posts/blog/**/*.md` から関連しそうな既存記事を探す。
   - タイトル、slug、カテゴリ、本文中の語を広めに検索する。
   - 指示されたファイルや用語が見当たらない場合は、大小文字、typo、表記ゆれを疑って探索する。
5. 既存記事候補と新規作成案を提示する。
6. ユーザーに対象を確認する。
   - 既存記事に追記
   - 新規記事を作成
   - ユーザーが別ファイルを指定
7. 編集方針を確認する。
8. ユーザーの OK 後にだけ Markdown を編集する。
9. `npm run posts:board` を実行して、`status` / `writingStatus` / メモ欄状態を確認する。

## 既存記事へ追記する場合

対象ファイルに `## メモ` 欄がある場合は、その中の末尾へ、選択されたモードで転記したメモ本文を追記する。

```md
## メモ

既存メモ

---

追加メモ（選択モードで転記したもの）
```

`---` は複数メモを区切るために追加してよい。

`原文＋軽い整理` を選んだ場合は、次の形にする。

```md
### 原文

ユーザーの原文

### 要約

- 原文の軽い要約

### 観点

- 記事化に役立つ観点
```

対象ファイルに `## メモ` 欄がない場合は、Markdown 末尾に `## メモ` 欄を作成し、選択されたモードで転記したメモ本文を入れる。

`## メモ` 見出しが複数ある場合は `BROKEN_MEMO` として扱い、修正方針を提示してユーザー確認を取る。

## 新規記事を作成する場合

新規記事が必要な場合は、編集前に次を提案する。

- `title`
- `slug`
- `categories`
- `tags`
- `status`
- `writingStatus`
- `priority`
- 作成先ファイルパス

`categories`・`tags`・`status`・`writingStatus`・`priority` は zod スキーマ（`src/content.config.ts`）で必須のため、値の中身に関わらずキー自体を frontmatter に必ず定義する。特に `tags` は `min(1)` の enum 配列で空配列を許さないため、デフォルト値では埋められない。適したタグが既存候補にあればそれを提案し、無理に当てはまらないものを入れない。既存候補に適したものがなければ、その旨をユーザーに伝えて確認する。

デフォルト値:

```yaml
thumbnail: "/images/thumbnail/noimage.webp"
githubUrl: ""
status: "private"
writingStatus: "todo"
priority: "none"
```

`publishedAt` と `updatedAt` は作業日の JST 日付にする。

frontmatter 例:

```yaml
---
title: "提案タイトル"
publishedAt: "YYYY-MM-DD"
updatedAt: "YYYY-MM-DD"
thumbnail: "/images/thumbnail/noimage.webp"
githubUrl: ""
categories:
  - 提案カテゴリ
tags:
  - 提案タグ
status: "private"
writingStatus: "todo"
priority: "none"
---
```

新規記事の初期形:

```md
## メモ

選択されたモードで転記したメモ本文
```

`原文＋軽い整理` を選んだ新規記事では、`## メモ` の中を `### 原文`、`### 要約`、`### 観点` に分ける。

## 構造の復元と記法

原文の内容と構造を分けて扱う。内容は文字列、構造は階層、並び、区切り、囲み、強調のような、文字ではない情報を指す。

Notion や他サービスからコピーした原文では、構造が失われてプレーンテキストに潰れていることが多い。失われた構造を Markdown の記法へ写し直すのは復元であり、加筆ではない。潰れたまま転記するほうが原文から遠い。転記モードに関わらず行ってよい。

### 不変条件

次をすべて満たす場合にだけ、記法へ置き換える。ひとつでも崩れるなら変換しない。

- 構造を表す記号を取り除いたテキストが、変換の前後で一致する
- 項目の順序と個数が一致する
- 変換の根拠が原文の中にある（インデント、行頭記号、区切り位置、揃い方）

### 復元の対象

- 行頭記号とインデントによる階層 → ネストした箇条書き
- タブ、連続スペース、`|` による列の揃い → GFM のテーブル。行側に見出しがあるなら HTML の `<table>` と `<th scope="row">`
- `□`、`☑`、`[ ]`、済・未済の印 → `- [ ]` / `- [x]` のチェックリスト
- 見出しの行と、その下だけが字下げされた塊 → トグル（`<details>`）または見出し
- 等幅で貼られたコマンドやコード → コードフェンス
- 注意や警告として区切られた塊 → `> [!NOTE]` などのコールアウト

これは例であって限定列挙ではない。原文に痕跡がある構造は、同じ判断で復元してよい。

### 判定

その構造として一貫している場合にだけ変換する。

階層として扱える例。下の行だけが字下げされ、記号の位置が揃っている。

```
- 調査
　　ー　現状の把握
```

```
- 調査
  - 現状の把握
```

列として扱える例。すべての行で区切りの数と位置が揃っている。

```
項目	状態	担当
設計	完了	自分
実装	着手	自分
```

```
| 項目 | 状態 | 担当 |
| --- | --- | --- |
| 設計 | 完了 | 自分 |
| 実装 | 着手 | 自分 |
```

変換しない例。字下げも記号も揃っておらず、階層なのか本文の続きなのか決められない。`ー` が長音か行頭記号かも判断できない。

```
- 調査
ー 現状の把握
	補足 ー ここは未定
```

判断がつかない場合は解釈を決めず、痕跡と読み方の候補を示してユーザーへ確認する。

### 禁止

- 文字列の変更。句読点の追加、語尾の変更、送り仮名や表記の統一を含む
- 語句の重複、省略、言い換え
- 項目の順序の入れ替え、分割、統合
- 原文に痕跡がない構造の付与

使える記法の一覧と雛形は、`astro-markdown-blog` のプレビュー記事詳細（`npm run dev` → `/preview/posts/<slug>`）の編集バーにある「記法」から確認できる。

## 提案時の注意

- slug は既存ファイル名と衝突しないように確認する。
- カテゴリは `src/constants/categories.ts` と `public/admin/config.yml` の既存候補から選ぶ。
- 既存カテゴリに合うものがない場合は、勝手に新規カテゴリを追加せず、カテゴリ追加案として提示してユーザー確認を取る。
- 新規カテゴリを提案する場合は、カテゴリ名、理由、影響ファイルを示す。
- タグは `src/constants/tags.ts` と `public/admin/config.yml` の既存候補から、内容に合うものだけ選ぶ。無理に当てはめない。
- 既存タグに合うものがない場合は、勝手に新規タグを追加せず、タグ追加案として提示するか、ユーザーに直接タグを確認する。
- メモ本文に秘密情報、トークン、個人情報らしき内容がある場合は、転記前にユーザーへ確認する。
- Notion から取得した本文も、選択された転記モードに従う。「原文のまま」「体裁を整える」では、意味を変えず、情報量を減らさず、原文の内容を保持する。「原文＋軽い整理」では、原文を残したうえで、要約と観点を別見出しに追記する。
