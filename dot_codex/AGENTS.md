- 返答は日本語。
- 指示されたファイルや用語が見当たらない場合は、大小文字の違い・タイポ・名前の勘違いを疑って探索してから報告する。
- push/pull などの Git 操作や破壊的な操作は、明示的な指示があるまで行わない。
- lint、test、build、型チェックなどの検証コマンドは、ユーザーが明示的に依頼しない限り実行しない。検証は CI / GitHub Actions で扱う。
- ユーザーが指定した手段・ツール・ファイル・方針が使えない場合でも、明示的な許可なく別手段へフォールバックしない。
- フォールバック候補がある場合は、元の目的との差分、失われる性質、リスクを説明し、ユーザーの合意を得てから実行する。
- 調査のための表記ゆれ確認、存在確認、読み取り専用の代替探索はこの限りではない。

## 一時成果物の運用

- 一時ファイルまたは一時ディレクトリを作る前に、commentary でパス、用途、削除タイミングを説明する。
- 作成した一時成果物のパスと用途を、そのターン中に保持する。
- 検証の完了、失敗、または不要化時には、自分が作成した一時成果物だけを削除する。
- 最終回答では、削除済みであることを報告する。保持する場合は、パスと理由を報告する。
- `/private/tmp` などに既に存在するものは、作成者と用途を確認できない限り削除しない。
- 一時成果物を作らずに済む場合は、標準出力またはツールの応答を優先する。

## 調査・情報源方針

- ライブラリ、フレームワーク、CLI、API、設定、ツールの使い方に関する提案・助言・回答は、公式ドキュメント（公式サイト / 公式リファレンス / 公式README）を一次情報として最優先で参照する。
- 提案や回答を行う前に、関連する公式ドキュメントを可能な限り確認し、仕様・推奨パターン・バージョン差異を踏まえて説明する。
- 記憶ベースで断定しない。特にバージョン依存・変更されやすい情報は、必ず確認してから回答する。
- 公式ドキュメントで確認できない内容は、その旨を明示したうえで、信頼できる情報源を補助的に参照し、推測を含む場合は推測であることを明示する。
- ユーザーに提案・アドバイス・質問回答を行う際は、事実（確認済み）と判断・推奨（解釈）を区別して説明する。
- 対象未特定の段階では広く探索し、特定後に公式情報で確認する。
- 公式優先は回答根拠に適用し、初動の探索範囲は狭めすぎない。
- 固有名詞の可能性がある語は表記ゆれや記号違いも含めて確認する。

## 実装前ゲート

- 仕様変更、設計変更、プロトタイプ変更、プロジェクト文書更新を含む依頼では、ファイル編集に入る前に必ず以下を提示し、ユーザーの明示的な合意を得る。
- 現状分析:
  - 該当箇所の現在の仕様、設計、実装、プロトタイプの状態
  - 問題点、矛盾、未定義事項、判断が必要な論点
- 選択肢:
  - 取りうる対応案を複数提示する
  - 各案のメリット、デメリット、トレードオフを説明する
- 推奨案:
  - どの案を推すかを理由付きで示す
- 反映範囲:
  - 更新対象ファイル、変更する論点、変更しない範囲を明示する
- 確認:
  - 「この方針で進めてよいか」を確認する
- ユーザーの明示的な OK が出るまで、`apply_patch` などによるファイル編集を行わない。
- 読み取り調査、差分確認、現状把握のためのコマンド実行はこの限りではない。

## レビュー・指摘の扱い

- 回答や成果物に対するユーザーのレビュー・指摘・懸念は、即修正指示として扱わない。まず指摘内容を分析し、同意点・懸念点・修正方針・必要なら修正文案を提示し、ユーザーの合意を得てから反映する。

## ADR候補の確認

- 設計、技術選定、ツール選定、文書運用、開発運用などの継続的な方針が会話中に確定、変更、却下された場合は、ユーザーがADRと言っていなくても `adr-workflow` を参照する。
- 同じ文脈の話に結論が付き、その文脈の作業が完了する時点で、その判断がADRへ残す条件を満たすか確認する。会話の途中で判断のたびに割り込まない。
- 該当する場合は、ADR候補、配置先とその理由、残す内容の簡略な要約を一度だけ提示し、ユーザーの承認を得る。
- 承認後は本文全体の再提示や二度目の確認を行わず、確認済みの配置先へADRを作成する。作成後は、対象ADRを開くための `v <ファイル名>` コマンドを提示する。
- 調査結果、作業ログ、実装手順、局所的で容易に変更できる詳細だけの場合はADRを作らない。

## UI変更前のデザイン文書確認

- UI / UXの提案、設計、実装、変更を行う前に、対象プロジェクトの `docs/README.md` など文書地図となる入口を確認し、今回の変更に関係するdesign文書を必ず読む。
- 全design文書を一括で読まず、変更対象に関係する原則、画面、状態、レイアウト、パターン、コンポーネント、tokenだけを読む。
- 関連文書を読む前に、一般的なデザイン原則や既存実装だけを根拠としてUI案を確定しない。
- 機能、振る舞い、対象ユーザー、利用文脈、受け入れ条件がUI判断に影響する場合だけ、関連するspecも確認する。
- 提案時には、参照した文書と、今回守るデザイン原則・制約を簡潔に示す。
- 指示が既存の要求・デザイン原則と矛盾する、恒久的な例外を作る、または複数の妥当な解釈がある場合は、意図を推測せずユーザーへ確認する。
- 既存原則に沿った変更や実装の追従だけで、文書更新を必須にしない。要求・デザイン判断そのものが変わる場合だけ、該当する文書系Skillに従って更新を提案する。

## スキル利用方針

- 反復的で重い手順は `~/.agents/skills` の Skill を優先する。
- 作業前に `~/.agents/skills` を確認し、該当 Skill があれば先に参照する。
- このファイルはコアルールの入口とし、詳細手順は Skill 側を正本にする。
- 該当 Skill に独自ルールがある場合は Skill を優先し、Skill に明記がない事項はこのファイルのコアルールを適用する。
- Skill を参照・使用した場合は、その Skill に書かれた手順、必須ルール、禁止事項、完了条件を必ず遵守する。参照だけして内容を無視したり、途中の都合のよい部分だけを実行して終了してはならない。
- Skill の指示と通常判断が衝突する場合は、Skill の指示を優先し、実行不能または不適切だと判断する場合は理由を明示してユーザー確認を取る。
- コードを書く・変更する作業では `coding-guidelines` Skill を参照する。
- プロジェクト文書の作成・更新・未記入項目の補完は、該当する文書系 Skill に従う。
- 設定ファイル、dotfiles、shell/editor/CLI 設定、`~/.config` 配下を編集する場合は `dotfiles-workflow` Skill を使い、`chezmoi source-path` が返す管理元を正本として編集し、原則 `chezmoi apply` まで行う。
